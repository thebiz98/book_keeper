1. WINDOWS SMART APP CONTROL VS. WINDOWS DEFENDER ANTIVIRUS
================================================================================
* What is Smart App Control (SAC)?
  SAC is a consumer cloud-reputation whitelist introduced in Windows 11.
  It blocks ANY executable that is not recognized by Microsoft's cloud catalog,
  even harmless "Hello World" programs or newly compiled local code.
  Because compilers (Rust, C++) generate new .exe files locally that have zero
  cloud history, SAC blocks them with "os error 4551".

* Does turning off Smart App Control create a security risk?
  Windows Defender Antivirus stays fully active: real-time scanning,
  cloud-delivered protection, ransomware guards, behavior monitoring and the
  firewall keep running. Turning off SAC only stops Windows from blocking
  unsigned developer tools (Cargo, Rust, newly compiled local binaries).
  Note: once SAC is turned off, Windows does not let you turn it back on
  without resetting/reinstalling Windows.

2. OPTION 1: NATIVE WINDOWS SETUP (ARM64 & x86_64)
================================================================================
Prerequisites: Open PowerShell as Administrator.

First, check your CPU architecture (it decides the C++ component in Step 2):
  $env:PROCESSOR_ARCHITECTURE      # ARM64  or  AMD64 (= x86_64)

--- STEP 1: Turn Off Smart App Control (Developer Requirement) ---
1. Open Windows Start Menu -> Search "Smart App Control".
2. Click "App & browser control" -> "Smart App Control settings".
3. Toggle to "Off".

--- STEP 2: Install Microsoft Visual Studio 2022 C++ Build Tools (MSVC) ---
Run in Administrator PowerShell.

x86_64 (AMD64) machines:
winget install Microsoft.VisualStudio.2022.BuildTools --override "--quiet --wait --norestart --nocache --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended" --accept-package-agreements --accept-source-agreements

ARM64 machines -- the ARM64 compiler component is REQUIRED and is NOT part of
the default VCTools workload. Without it, every Rust build fails with
"error: linker `link.exe` not found":
winget install Microsoft.VisualStudio.2022.BuildTools --override "--quiet --wait --norestart --nocache --add Microsoft.VisualStudio.Workload.VCTools --add Microsoft.VisualStudio.Component.VC.Tools.ARM64 --includeRecommended" --accept-package-agreements --accept-source-agreements

Build Tools already installed without ARM64? Add just the component:
& "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\setup.exe" modify --installPath "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools" --add Microsoft.VisualStudio.Component.VC.Tools.ARM64 --passive --norestart

(GUI alternative: Visual Studio Installer -> Build Tools 2022 -> Modify ->
 Individual components -> "MSVC v143 - VS 2022 C++ ARM64/ARM64EC build tools".)

Check that the ARM64 linker exists (should print True):
Test-Path "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Tools\MSVC\*\bin\Hostarm64\arm64\link.exe"

(Alternative via Browser):
Download from https://visualstudio.microsoft.com/visual-cpp-build-tools/
Run the installer and check: "Desktop development with C++"
(on ARM64 also tick the ARM64 build tools component above).

--- STEP 3: Install Node.js (LTS) ---
Method A: Portable Clean Install (Bypasses all MSI installer permission issues):
# Run in PowerShell:
curl.exe -L -o "$env:TEMP\node.zip" "https://nodejs.org/dist/v22.11.0/node-v22.11.0-win-arm64.zip"
Expand-Archive -Path "$env:TEMP\node.zip" -DestinationPath "$env:LOCALAPPDATA\Programs" -Force
Rename-Item -Path "$env:LOCALAPPDATA\Programs\node-v22.11.0-win-arm64" -NewName "nodejs" -Force
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path", "User") + ";$env:LOCALAPPDATA\Programs\nodejs", "User")

(For x86_64 Intel/AMD machines, replace "win-arm64.zip" with "win-x64.zip").

Method B: Via Winget:
winget install OpenJS.NodeJS.LTS

--- STEP 4: Install Rust & Cargo Toolchain ---
Run in Administrator PowerShell:
winget install Rustlang.Rustup

(Alternative via direct download):
For ARM64: curl.exe -o "$env:TEMP\rustup-init.exe" "https://win.rustup.rs/aarch64"
For x86_64: curl.exe -o "$env:TEMP\rustup-init.exe" "https://win.rustup.rs/x86_64"
Start-Process -Wait "$env:TEMP\rustup-init.exe" -ArgumentList "-y"

Check the toolchain matches your CPU:
rustup show active-toolchain   # ARM64: stable-aarch64-pc-windows-msvc
                               # x64:   stable-x86_64-pc-windows-msvc

--- STEP 5: Microsoft Edge WebView2 Runtime ---
Pre-installed on Windows 10/11 by default.
If missing: winget install Microsoft.EdgeWebView2Runtime

3. OPTION 2: WSL2 SETUP (KEEPING SMART APP CONTROL "ON" ON WINDOWS)
================================================================================
If your Windows 11 machine must keep Smart App Control strictly ON:
Run Rust inside WSL2 (Linux). Windows SAC does not inspect or block Linux binaries.
On Windows 11, WSLg automatically forwards the Linux GUI window onto your Windows desktop.

--- STEP 1: Enable & Launch WSL2 (Ubuntu) ---
In Windows PowerShell:
wsl --install -d Ubuntu

--- STEP 2: Install Linux C/C++ Build Essentials & Tauri Linux Dependencies ---
Inside your Ubuntu terminal:
sudo apt update && sudo apt upgrade -y
sudo apt install -y build-essential curl wget file libssl-dev libgtk-3-dev libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev

--- STEP 3: Install Node.js LTS in WSL ---
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

--- STEP 4: Install Rust & Cargo in WSL ---
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"

--- STEP 5: Database Path Configuration ---
By default, SQLite creates the database in Linux: ~/.local/share/com.bookkeeper.app/shop.db
If you want the database stored on your Windows C: drive accessible via File Explorer, set:
export BOOK_KEEPER_DB_PATH="/mnt/c/Users/<YourWindowsUsername>/AppData/Roaming/com.bookkeeper.app/shop.db"
(SQLite over /mnt/c is slower and its file locking is less reliable; prefer the
 Linux default for day-to-day use.)

4. OPTION 3: PURE NATIVE LINUX SETUP (Ubuntu / Debian / Arch / Fedora)
================================================================================
--- Ubuntu / Debian ---
sudo apt update
sudo apt install -y build-essential curl wget file libssl-dev libgtk-3-dev libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash - && sudo apt install -y nodejs
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"

--- Fedora ---
sudo dnf groupinstall "C Development Tools and Libraries"
sudo dnf install webkit2gtk4.1-devel openssl-devel curl
sudo dnf install nodejs
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y

--- Arch Linux ---
sudo pacman -Syu --needed base-devel webkit2gtk-4.1 openssl curl nodejs npm rustup
rustup default stable

6. PROJECT INITIALIZATION & RUNNING THE APP (DEVELOPMENT, NO .EXE)
================================================================================
Development mode runs the app straight from source. Nothing is installed and
no release build is made. Use it while iterating.

Navigate to the project root directory:
cd C:\custom_apps\book_keeper          (or /path/to/book_keeper)

--- First Time Initialization ---
npm install          # installs frontend deps + the Tauri CLI (@tauri-apps/cli)

--- Run in Development Mode ---
npm run tauri dev    # same as: npx tauri dev

What it does: starts the Vite dev server on http://localhost:1420, compiles the
Rust backend (debug), and opens the "Book Keeper" window. The first compile
takes a few minutes; later launches take about 10 s.
  * Saving a .ts/.tsx/.css file -> the window hot-reloads instantly.
  * Saving a .rs file           -> Rust recompiles and the app restarts.
  * Closing the window or pressing Ctrl+C in the terminal stops everything.

--- Windows: Desktop Shortcut (no install, no .exe build) ---
(Development machines. A machine that only runs the app should use the
scripts\launch.cmd shortcut in section 8, Option A+.)
The repo ships scripts\dev-launch.cmd, which runs `npx tauri dev` from the
project folder (and runs `npm install` first if node_modules is missing).
Create a desktop shortcut to it once, from PowerShell in the project root:

$proj = (Get-Location).Path
$desk = [Environment]::GetFolderPath('Desktop')
$lnk = (New-Object -ComObject WScript.Shell).CreateShortcut("$desk\Book Keeper (dev).lnk")
$lnk.TargetPath = "$proj\scripts\dev-launch.cmd"
$lnk.WorkingDirectory = $proj
$lnk.IconLocation = "$proj\src-tauri\icons\icon.ico"
$lnk.WindowStyle = 7          # start the console minimized
$lnk.Save()

Double-click "Book Keeper (dev)" on the desktop. A minimized console holds the
dev server and logs; closing it also closes the app. Closing the app (or a
Restore from backup, which closes the app) also closes the console:
scripts\dev-launch.ps1 watches the app and stops the dev server once it is gone,
unless a Rust rebuild is relaunching it. If startup fails, the console stays open
with the error.

--- Where the data lives ---
The real backend stores everything in one SQLite file:
  Windows : %APPDATA%\com.bookkeeper.app\shop.db
  Linux   : ~/.local/share/com.bookkeeper.app/shop.db
  macOS   : ~/Library/Application Support/com.bookkeeper.app/shop.db
Override it with the BOOK_KEEPER_DB_PATH environment variable, e.g. a
throw-away database for experiments (PowerShell):
  $env:BOOK_KEEPER_DB_PATH = "C:\temp\bk-scratch.db"; npm run tauri dev
Dev mode, the .exe and the installed app all share the same default database.

7. UI ONLY (MOCK BACKEND) VS. UI + REAL BACKEND
================================================================================
No flag or config switch is needed. src/api/index.ts picks the client at
runtime: inside a Tauri window it uses TauriClient (real Rust backend + SQLite
over IPC); in a plain browser it falls back to MockApiClient (in-memory fake
data, src/api/mock/).

--- UI with the MOCK backend (no Rust needed, fastest UI iteration) ---
npm run dev
Then open http://localhost:1420 in Edge/Chrome. Mock data is in memory only
and resets on every page reload. Good for layout/styling/flow work; it does
NOT exercise real validation, FIFO costing, or database behaviour.

--- UI with the REAL backend ---
npm run tauri dev        (or the desktop shortcut from section 6)
The Tauri window talks to the Rust backend, which reads and writes shop.db.

Tip: while `npm run tauri dev` is running, http://localhost:1420 in a normal
browser still shows the MOCK version (the browser has no Tauri IPC), so you
can compare the two side by side.

8. BUILDING THE .EXE AND INSTALLERS, INSTALLING, RUNNING
================================================================================
--- Build ---
From the project root (PowerShell or cmd, see section 9 about Git Bash):
npm run tauri build

This runs `npm run build` (tsc + Vite production bundle), compiles Rust in
release mode, embeds the UI inside the exe, and produces (ARM64 example; on
x64 the names say x64):

  target\release\book-keeper.exe                                   (~12 MB, portable)
  target\release\bundle\msi\Book Keeper_0.1.0_arm64_en-US.msi       (~4.6 MB, MSI installer)
  target\release\bundle\nsis\Book Keeper_0.1.0_arm64-setup.exe      (~3 MB, setup wizard)

Build time: about 2 minutes on a warm cache. The first build downloads the WiX
and NSIS installer tools automatically (internet needed once). To build only
one installer type:  npm run tauri build -- --bundles nsis   (or msi)

--- Option A: Run the portable exe (no install) ---
Double-click target\release\book-keeper.exe, or put a shortcut to it on the
desktop. The UI is embedded, so no dev server is needed. It needs only the
WebView2 runtime, which ships with Windows 10/11. Copy the exe anywhere;
it uses the same %APPDATA% database as dev mode.

--- Option A+: Shop machine shortcut (clone, then run; recommended) ---
For a machine that only RUNS the app (development happens elsewhere).
scripts\launch.cmd (logic in scripts\launch.ps1) does, on every launch:
  1. git pull --ff-only   (skipped with a note when offline or not possible)
  2. if the checked-out commit differs from target\release\.built-commit, or
     the exe is missing: npm ci (only when package-lock.json changed), then
     npx tauri build --no-bundle   (release exe, no installers; a few minutes)
  3. starts target\release\book-keeper.exe and closes the console.
No change since the last build -> the app opens immediately. A failed build
keeps the console open with the error and offers to open the previous exe.
A second launch while the app is open does not start a second copy.
Create the shortcut once, from PowerShell in the project root:

$proj = (Get-Location).Path
$desk = [Environment]::GetFolderPath('Desktop')
$lnk = (New-Object -ComObject WScript.Shell).CreateShortcut("$desk\Book Keeper.lnk")
$lnk.TargetPath = "$proj\scripts\launch.cmd"
$lnk.WorkingDirectory = $proj
$lnk.IconLocation = "$proj\src-tauri\icons\icon.ico"
$lnk.WindowStyle = 7          # console starts minimized; it pops up only to build or show an error
$lnk.Description = "Book Keeper (updates and rebuilds when needed)"
$lnk.Save()

Push only reviewed, merged work to main: the shop machine picks it up on the
next launch. target\debug is not used here and can be deleted to free space.

--- Option B: Install ---
Double-click Book Keeper_0.1.0_arm64-setup.exe (NSIS, installs per user, no
admin) or the .msi (Windows Installer, per machine). It adds Start Menu
(and optional desktop) shortcuts and an entry in Settings -> Apps.
Because the build is unsigned, Windows SmartScreen may show "Windows protected
your PC": click "More info" -> "Run anyway". With Smart App Control ON,
unsigned installers are blocked outright.

--- Uninstall ---
Settings -> Apps -> Installed apps -> Book Keeper -> Uninstall.
The database in %APPDATA%\com.bookkeeper.app is NOT removed. Delete it by hand
if you want a clean slate (back it up first; it holds all shop records).

--- ARM64 vs x64 builds ---
The build targets the machine's own architecture. An ARM64 build runs only on
ARM64 Windows. To produce an x64 build from an ARM64 machine:
  rustup target add x86_64-pc-windows-msvc
  npm run tauri build -- --target x86_64-pc-windows-msvc
(needs the default x64 MSVC tools, which the VCTools workload installs).

9. RUNNING THE TEST GATE ON WINDOWS
================================================================================
run_e2e_tests.sh runs: cargo test, cargo clippy -D warnings, tsc, vitest, vite
build. On Windows, run the steps from PowerShell or cmd:

cd src-tauri; cargo test; cargo clippy -- -D warnings; cd ..
npx tsc --noEmit
npx vitest run
npx vite build

Do NOT run cargo from Git Bash: Git's /usr/bin/link.exe (a GNU file-linking
utility) comes before the MSVC linker on PATH, and every build fails with
"link: extra operand ...". This also applies to `bash run_e2e_tests.sh`.

10. PLATFORM NOTES (WHAT IS AND ISN'T WINDOWS-SPECIFIC)
================================================================================
Getting the app running on Windows needed NO Windows-specific code changes.
The changes made on 2026-11-22 were all platform-neutral:
  * package.json: added @tauri-apps/cli (needed to run Tauri at all) and
    happy-dom (Vitest environment; it was in vite.config.ts but missing from
    package.json).
  * src-tauri/build.rs: rewrote icon files on every build, which made
    `tauri dev` rebuild forever on any OS. It now writes only missing icons.
  * Four small clippy fixes required by the newer Rust 1.100 lints (same
    behaviour, including rejecting NaN bundle multipliers).

Backend (Rust): cross-platform. There is no cfg(windows)/cfg(unix) code.
SQLite is bundled (rusqlite "bundled"), so no system SQLite is needed. File
paths come from Tauri's app_data_dir() plus PathBuf.

UI (React): cross-platform. The same bundle runs in every OS webview.

Webview (this part does differ per OS; Tauri chooses it, not our code):
  Windows : Microsoft Edge WebView2 (Chromium), pre-installed on Win 10/11
  Linux   : WebKitGTK 4.1 (libwebkit2gtk-4.1)
  macOS   : WKWebView (Safari engine)
Keep CSS/JS within what both Chromium and Safari/WebKit support; Vite targets
chrome105 on Windows and safari13 elsewhere (vite.config.ts). Only Windows has
been exercised in a real window so far.

Windows-only bits that are harmless elsewhere:
  * #![windows_subsystem = "windows"] in main.rs hides the console in release
    builds; other OSes ignore it.
  * scripts\dev-launch.cmd is a Windows convenience; on Linux/macOS just run
    `npm run tauri dev`.

Known cross-platform follow-up: the bundle identifier "com.bookkeeper.app"
ends in ".app", which Tauri warns conflicts with the macOS app bundle
extension. Changing it moves the default data folder on every OS (existing
shop.db would need to be moved), so it is left as is until macOS is targeted.

11. APP CONFIG, BACKUPS AND RESTORE
================================================================================
--- src-tauri/app.config.json (compiled in) ---
{ "testingMode": true, "backup": { "intervalHours": 24, "retentionDays": 7, "onExit": true } }
  testingMode            true shows the "Testing tools" card in Settings (clear
                         transactions / clear all data). The backend refuses
                         resets when it is false. SET IT TO false FOR A REAL
                         SHOP BUILD.
  backup.intervalHours   minimum age of the last auto backup before a new one.
  backup.retentionDays   auto and pre-reset backups older than this are deleted.
  backup.onExit          also back up when the app closes (see below).
The file is compiled into the program, not read at run time. After changing it,
rebuild (npm run tauri build) or restart `npm run tauri dev`.

--- Backup folder ---
Chosen in Settings with the native folder picker (no typed path). The choice is
saved in the database. "Use default" returns to
  %APPDATA%\com.bookkeeper.app\backups
which is created automatically.

--- When backups happen ---
  * At startup, when the last auto backup is at least intervalHours old; then
    checked again every hour while the app is open.
  * On close, when the database changed since the last auto backup.
  * Manually: Settings -> Backup Now (or Ctrl+B).
  * Before every data reset (testing tools), always.

--- File names ---
  book_keeper_backup_YYYYMMDD_HHMM.db    manual
  book_keeper_auto_YYYYMMDD_HHMM.db      automatic
  book_keeper_prereset_YYYYMMDD_HHMM.db  written just before a reset

--- Rotation ---
Auto and pre-reset backups older than retentionDays are deleted, but the newest
auto backup is always kept. Manual backups are never deleted.

--- Restoring a backup ---
1. Close Book Keeper completely.
2. Copy the backup file over shop.db (%APPDATA%\com.bookkeeper.app\shop.db,
   or the path in BOOK_KEEPER_DB_PATH).
3. Delete shop.db-wal and shop.db-shm next to it, if they exist.
4. Start the app.

--- If shop.db is deleted ---
The app creates a new, empty database at the next start. All data is lost unless
you restore a backup as described above.

12. TROUBLESHOOTING
================================================================================
"error: linker `link.exe` not found"
  -> ARM64 machine without the ARM64 MSVC component. See section 2, Step 2.

"link: extra operand '...rcgu.o'"
  -> cargo was run from Git Bash. Use PowerShell or cmd (section 9).

"os error 4551" / build scripts blocked
  -> Smart App Control is on. See section 1, or use WSL2 (section 3).

`tauri dev` keeps printing "File src-tauri\icons\... changed. Rebuilding"
  -> An old build.rs. Pull the fixed version (writes icons only if missing).

"Cannot find package 'happy-dom'" when running vitest
  -> Run `npm install` (happy-dom is now a devDependency).

"Port 1420 is already in use"
  -> Another dev server is still running. Close its console, or:
     Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object CommandLine -match vite | ForEach-Object { Stop-Process -Id $_.ProcessId }

Blank window
  -> WebView2 is missing: winget install Microsoft.EdgeWebView2Runtime
